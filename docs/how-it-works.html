FreeCAD addon · how it works

FeatureNamer internals

How a pure-Python addon adds a Name field to every Sketcher and PartDesign task dialog, names features after the feature they are built from, and asks for a name only when it should, without hooking into any FreeCAD C++ code.

Targets FreeCAD 1.1+ (tested on 27.1 dev) Scope Sketcher and PartDesign edit dialogs Core changes none, Python only User manual avongil.github.io/FreeCAD-FeatureNamer

Overview

FeatureNamer only works on features while they are being edited. It doesn't scan the document, add properties, or store anything in the .FCStd file. The only thing it ever changes is obj.Label. The work is split into three parts:

  • A Gui document observer (gui/controller.py). It learns when a view provider enters or leaves edit mode, and decides whether to name the feature, wait, or ask.
  • Widgets (gui/widgets.py): the Name field placed at the top of the task panel, and the Name feature popup.
  • Pure rules (core/naming.py): what counts as a default label, and how postfixes are added, stripped and carried over. This part has no FreeCAD imports and is unit-tested.

Startup

init_gui.py registers everything when the module is imported. That way the Tools menu entry exists before the first workbench builds its menus. An earlier version deferred this, and the entry only appeared after switching workbenches. It registers four things:

  1. The command FeatureNamer_Settings, with CmdType: ForEdit so it stays clickable while a sketch is open.
  2. Gui.addDocumentObserver(controller). This is a Gui observer, because edit-mode signals (slotInEdit, slotResetEdit) only exist on the Gui document.
  3. Gui.addPreferencePage(FeatureNamerPreferencesPage, "FeatureNamer").
  4. A workbench manipulator that inserts the command after Std_DlgParameter in the Tools menu.

The preference page class name must be globally unique. FreeCAD identifies Python preference pages by class name. Until 0.2.1 the class was called PreferencesPage, and when another addon (Resolve_Mode) used the same name, its preferences group showed FeatureNamer's page.

The edit lifecycle

FreeCAD has no signal for "a task dialog finished building" or "the user picked a base feature". So the controller combines two edit-mode signals, a deferred call, and a 400 ms watchdog that runs only while a target is in edit.

  1. slotInEdit(vp) If vp.Object.TypeId starts with Sketcher:: or PartDesign:: and isn't excluded (the default exclusion is PartDesign::Body), the object becomes current. Everything else is deferred with QTimer.singleShot(0), because the task dialog doesn't exist yet when this slot fires.
  2. _on_enter() If the label is a default one and the object hasn't been asked about, the controller first tries to derive a name from the base feature, silently. If the feature depends on a base that hasn't been picked yet (for example a pattern opened with nothing selected), it sets waiting_for_base instead. It then injects the Name field and starts the watchdog. If the feature is still unnamed and PromptIfUnnamed is on, it shows the popup.
  3. _tick() Every 400 ms while in edit, the watchdog does three things:
    • It checks that getInEdit() is still this object. If not, it ends the edit, because a reset signal can be missed.
    • If it's waiting for a base, it tries to derive the name again.
    • It re-injects the Name field if the dialog rebuilt its panel. The Sketcher does this, for example.
  4. _edit_ended() Runs when slotResetEdit or the watchdog notices the edit ended, whichever comes first. It is idempotent. It removes the field, stops the timer and clears current. If AskOnClose is on, or the feature was waiting for a base, it schedules _after_close.
  5. _after_close(obj) It stops if the object was deleted (Cancel on a new feature deletes it), if the object already has a real name, or if it was already asked about. Otherwise it derives a name, or shows the popup, inside its own transaction, because the edit transaction is closed by now.

The Name field

There is no public API for adding a widget to another command's task dialog. So the addon finds the panel by its Qt class name and inserts a frame at the top of its box layout:

for w in Gui.getMainWindow().findChildren(QtWidgets.QWidget):
    if w.metaObject().className() == "Gui::TaskView::TaskPanel" and w.isVisible():
        w.layout().insertWidget(0, NameBox(obj, w))

The frame has the object name FeatureNamerBox and keeps a reference to its object, so the watchdog can tell whether the right field is already in place. Its behaviour:

  • textEdited writes obj.Label on every keystroke. The tree updates live, and the rename becomes part of the dialog's open transaction (see Undo and Cancel).
  • editingFinished adds the type postfix, but only if the text was changed. That way, clicking into the field and back out never turns Sketch009 into Sketch009_SKT.
  • Enter finishes the edit and hands keyboard focus back to the 3D view, so Sketcher shortcuts work again.
  • FocusNameField moves the cursor into the field once per edit. It only applies when the popup is off and the label is still a default one. A feature that was named after its base keeps the cursor in its first input, for example Length.

Naming rules

All of this lives in core/naming.py and has no FreeCAD dependency.

What counts as a default label

A label is a default one if it equals the internal Name, or if it's the alphabetic part of the name followed only by digits. Because the comparison uses the untranslated internal name, it works in any interface language.

Postfixes and naming from the base feature

The postfix table maps a TypeId to a postfix, for example PartDesign::Pad=_PAD. add_postfix appends the postfix unless the text already ends with it (ignoring case). A feature's base is found through:

  • Profile: pads, pockets, revolutions, pipes, lofts and holes
  • Base: only for dress-up features (fillet, chamfer, draft, thickness)
  • Originals: patterns and mirrors
derive_label("OutsideMoat_SKT", all_postfixes, "_PAD")  -> "OutsideMoat_PAD"
derive_label("OutsideMoat_PAD", all_postfixes, "_FIL")  -> "OutsideMoat_FIL"
derive_label("Bracket_SLOFT",   all_postfixes, "_MIR")  -> "Bracket_MIR"    # longest postfix wins: _SLOFT, not _LOFT
derive_label("Plate",           all_postfixes, "")      -> None             # no postfix: would only copy the name

Nothing is derived from a base that still has a default label. Pad from Sketch009 stays unnamed, and the popup or the close prompt handles it. Renaming the sketch later doesn't rename features that were already built from it.

Who has been asked

Two sets stop the addon from nagging: asked (popup shown when entering edit) and asked_close (prompt shown after OK). A derived name adds the object to both.

The key is (document name, obj.ID), not the internal name. FreeCAD reuses internal names: delete Sketch009, draw a new sketch, and it's Sketch009 again. Up to 0.2.1 the sets were keyed by name, so the new sketch counted as already asked and the close prompt never appeared. obj.ID is never reused within a document. This was fixed in 0.2.2.

Undo and Cancel

  • While editing, label changes go straight into the transaction the task dialog opened. Cancel then reverts the name together with the feature, and one Undo step removes both.
  • After the edit, the close prompt runs when that transaction is already committed. It opens its own Rename … transaction, and aborts it if the rename raises.
  • Deleted features: is_alive(obj) checks doc.getObject(obj.Name) is obj before any late rename. Cancel on a new feature deletes it, and FreeCAD may hand the same name to a later object.

Developer questions

Why a 400 ms timer instead of signals?

The events FeatureNamer needs don't have signals: a task dialog rebuilding its panel, a base feature being picked inside a dialog, or an edit ending without slotResetEdit. The timer only runs while a Sketcher or PartDesign object is in edit, does little per tick, and stops on the first sign that the edit ended.

Isn't searching by Gui::TaskView::TaskPanel fragile?

Yes. It's the one internal detail the addon depends on. If the task view were restructured, the Name field would stop appearing, but naming from the base feature and the popups would keep working, because they only use public APIs. A public header hook on Gui::TaskView::TaskDialog would remove this dependency (see the proposal for core).

Does it change files or add properties?

No. It only sets Label, which is a standard property. Files are identical to ones named by hand, and they open the same without the addon.

Why is the popup modal?

It appears at a moment when FreeCAD expects the next action, entering edit or just after OK. A modal exec() keeps the rename inside the right transaction and stops the user editing a half-named feature. Skip closes it and records that the object was asked, so it doesn't come back for that object.

Does it work in other languages?

Detecting default labels uses the internal Name, which is never translated, so yes. The addon's own interface text is English only for now. The strings are wrapped for translation, but no translations ship yet.

Limits

  • Edit mode only. Only objects opened through setEdit() are handled. Commands that don't edit a document object, such as Part ▸ Extrude, aren't covered.
  • Keyboard focus. While the Name field has focus, single-key Sketcher shortcuts type into it. Enter returns focus to the 3D view. This is why FocusNameField is off by default.
  • Duplicate labels. If duplicate labels aren't allowed, FreeCAD appends a suffix. The field shows the final label once editing is finished.
  • No retroactive renames. Features already built from a sketch keep their names when the sketch is renamed later. Opening such a feature for editing derives the name at that point.
  • Widget search cost. findChildren walks the main window's widget tree on every watchdog tick. This hasn't been noticeable, but it isn't free.

Tests

tests/test_naming.py (pytest, no FreeCAD needed) covers default labels, adding, stripping and deriving postfixes, and parsing the postfix table. The edit-mode behaviour was verified in the FreeCAD 27.1 dev GUI with scripted sessions:

  • A Pad created from a named sketch gets …_PAD, with the Name field in place.
  • Editing an existing default-named Pad derives its name.
  • An unnamed sketch gets the close prompt, including a sketch that reuses a deleted sketch's internal name.
python -m pytest -q tests
